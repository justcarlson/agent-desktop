# Linux Shell Surfaces and Notifications (Sub-phase 3.14) - Plan

## Goal Capsule

- **Objective:** on GNOME, an agent can snapshot the dock (`taskbar`), the top-panel tray (`system-tray`), the message list (`action-center`) and the system menu (`quick-settings`, included only if U1 item 5 measures its round trip; otherwise not advertised with the reason written down), act on their refs through the ordinary `click` / `find` / `snapshot --surface` path, and run `list-notifications`, `dismiss-notification`, `dismiss-all-notifications`, `notification-action` and `wait --notification` with every effect proved by independent observation. On a desktop where the measured mechanism does not exist, every one of those commands says so with `PLATFORM_NOT_SUPPORTED` and a suggestion naming the missing piece, never an empty list or a silent pass.
- **Means:** Linux-crate code only. Detect the three independent GNOME facts (notification daemon, shell tree, tray watcher); resolve the shell as its own root without putting it back into ordinary window listings; read notifications from the message-list copy of the shell tree; mutate them only by pointer clicks inside the open message list (the only mechanism the probes found, `L21-7`, `L21-11` to `L21-13`); deliver tray activation and menu picks over D-Bus when the item offers the method, and by pointer otherwise (KTD1-KTD16).
- **Menu surfaces (owned here by the owner's decision):** an agent that opens a popup menu (GTK3 menu or header-bar popover, GTK4 popover or context menu, Qt `QMenu`, Chromium menu) by `click`, `right-click` or `expand` sees `menu` in `data.surfaces` after that action, can run `snapshot --surface menu` and `find --surface menu`, and can act on the item refs. `supported_surfaces` gains `menu`. The measured roles, states and window types of each toolkit's menus come first (U1 items 12 to 16, ledger area `L32`); the evidence from the 3.7 dogfood is that `right-click` on Calculator and `expand` on a Text Editor menu button add nine unnamed `menuitem` nodes to the window snapshot while `data.surfaces` lists only the window. Core already has `SnapshotSurface::Menu` and `Popover` (`crates/core/src/snapshot_surface.rs`), so no core change is planned (R16); a core need found by U1 items 12 to 16 becomes an owner item.
- **Authority:** `docs/phases.md` §3.14 and the two subsections under it, as corrected here where the code or the ledger disproves them (R14). The pre-code probe rows `L21-1` to `L21-36` are the measurements this plan stands on; new measurements of this sub-phase use ledger area `L32`.
- **Stop conditions:** stop if a requirement needs a line under `crates/core` (every known case is an owner item, KTD2); if 3.5, 3.6, 3.8 or 3.9 land without strict resolution, `hit_test`, X11 pointer delivery, the session-bus facility or the process-attribution launch recipe (a missing shell seam in 3.5's gate or 3.6's `hit_test` is not a stop: U4 edits those files directly and the PR names the edits); if U1 shows a virtual node cannot pass core's identity and actionability contracts (KTD9: then tray menu picks fall back to the pointer route and the D-Bus pick becomes an owner item); or if no private shell can be health-gated up on the box (`L21-34`).
- **Execution profile:** U1 first (it measures what the box could not: X11 pointer on the shell, the end-to-end shell-ref contract, QuickSettings, the label structure that separates the time label, the virtual-node fit, HiDPI, and the menu facts of items 12 to 16); U2 (documentation and ledger corrections) may run in parallel with U1; U3 after U1; U4 after U3; U5 after U4; U6 after U4; U7 after U5 and U6; U8 after U4; U9 after U8 and U6; U10 (sandbox closure) is independent after U1 and may run on a hosted runner at any point; U14 to U16 (menu surfaces) need only U1 items 12 to 16 and 3.11's menu predicate, not U3 to U9, so they run in parallel with every notification and tray unit; U11 after U7, U9, U10, U16; U12 (dogfood) after U11; U13 last, because it records every disposition. The lane split that makes this parallel is under "Parallel Lanes and Frozen Interfaces".
- **Finishes and ships:** the implementer runs the box measurements, commits, and opens one PR stacked on the 3.13 branch with `gh stack`, from `feat/linux-3.14-shell-notifications`, into `feat/linux-adapter`; nothing merges to `main` and nothing is published. The 3.13 branch name (`feat/linux-3.13-ffi-npm-release`) is taken from that plan; confirm it at the cut.

## Product Contract

### Summary

Give Linux the DE-specific half of parity that Windows 2.14 and macOS Notification Center already have. After this sub-phase a Linux agent on GNOME 46 can read the notifications the shell retains, dismiss one, dismiss all or all of one app's, and press a notification action; can snapshot and act on the dock, the tray, the message list and the system menu; can activate a tray item and pick a tray menu entry; and can wait for a new notification. The sandbox legs the roadmap listed as procedures (snap interfaces, Flatpak override) are measured and their exact text enters the docs.

### Problem Frame

GNOME is the one desktop with measured evidence, and the evidence overturns most of what the roadmap assumed (`L21`, GNOME Shell 46.0, mutter 46.2, AT-SPI 2.52, private shells only):

- **There is no way to learn a notification's daemon id from the shell.** Four notifications posted by a separate sender, every node and its 24 to 30 descendants dumped with attributes, relations and descriptions: nothing carries the id, node paths are a global counter, tree order is newest-first by update and moves on a replace, and identical entries are indistinguishable (`L21-7`, `L21-8`). `CloseNotification(id)` therefore dismisses only an id the caller itself saw returned by `Notify`. The adapter never posts, so it never holds one; a blind close would close a stranger's notification (`L21-8`). The roadmap's "the only per-notification dismissal on GNOME" is false in both halves.
- **The shell does expose per-entry controls, and they take a pointer.** In the open message list each entry has two unnamed `push button` nodes in its header (expand, then close) and a named action button that has real extents only after expansion; every one has `nactions: 0`. A click on the close button makes the daemon emit `NotificationClosed(id, 2)` and removes the entry while other apps' entries stay; a click on an expanded action button makes the daemon emit `ActionInvoked` and then close the notification; `Clear all notifications` closes every list entry (`L21-11` to `L21-13`). Dismiss and action are therefore headed-only, which matches core's existing rule that notification mutation needs `allow_focus_steal` (`crates/core/src/commands/notification_policy.rs`).
- **One notification is two nodes.** A banner copy at depth 5 and a list copy at depth 15 (depth reaches 21 with 19 entries). Clear-all removes the list copy and leaves the banner copy for 25 seconds; `CloseNotification` removes both. Only the list copy is authoritative and the fingerprint `wait --notification` compares must not see the banner (`L21-14`). The shell keeps a bounded number per source: 40 posts from four apps left 12 entries (`L21-15`).
- **Empty is a footer, not an absence.** Zero notifications with the list open shows `Do Not Disturb`, its switch and the clear-all push button (disabled), and on some shell versions `No Notifications` (depth 10); an unreadable tree has none of that and must be an error because the return type has no partial flag (`L21-16`, `L32-31`).
- **Three independent things can each be missing.** The daemon (`GetServerInformation` answers `gnome-shell`; the owner is a `gjs` helper, not the shell, `L21-5`; killing it makes the name unactivatable while old entries stay in the tree, `L21-6`), the shell tree (a shell that never re-registers on a replaced accessibility bus is the measured way to have the daemon with no tree, `L21-4`; `toolkit-accessibility=false` does not hide it, `L21-3`), and the tray watcher (absent without the AppIndicator extension, present-and-empty with it, `L21-32`).
- **The shell is a real, readable, clickable AT-SPI app.** The registry app whose pid owns `org.gnome.Shell` has one `window` child named `""` at `[0,54,87,55]` whose subtree is the whole shell (`L21-1`, `L21-2`); extents of valid on-screen nodes are reliable click targets (more than 25 clicks all landed, `L21-21`); a point query returns a coarse container and cannot confirm a shell target (`L21-20`); an autohidden dock sits at `x=-84` and cannot be clicked, while a merely negative origin is not a reason to refuse (`L21-21`). A full shell walk costs 1.9 s, the list subtree 29 ms, an index-chain re-resolve 2.9 ms (`L21-33`).
- **Tray activation has three different meanings.** On the shell, a primary click opens the menu (dbusmenu `opened`) and sends no SNI method; a middle click delivers `SecondaryActivate` (KDE-style) or `XAyatanaSecondaryActivate` (Ayatana-style); a right click opens the menu (`L21-26`). `Activate` exists only on items that list it, and a direct call is proved by the receiver's own log (`L21-25`). A direct `Event(id,"clicked")` on a dbusmenu reaches the receiver even for a disabled item, a separator and a nonexistent id, so the adapter must validate before sending (`L21-27`). A well-known-name reference follows a restarted service; a unique-name reference fails closed (`L21-30`). Passive items keep a panel node, so hidden is the `Status` property, not extents (`L21-31`). The watcher lists two measured registration forms, `name@path` and a bare bus name (`L21-24`); a slash form is parsed defensively and is unmeasured.
- **Four roadmap sentences are false** (`L21` section 3) and are corrected in U2; the remaining 3.14 roadmap sentences are incomplete (shell kinds not enumerated, dependencies missing 3.5, 3.6, 3.8, 3.9; `Notify` "signals"; "history within the daemon session" in a stateless CLI).

### Requirements

**Environment and shell roots**

- R1. A detector reports the daemon, the shell tree and the tray watcher as three separate states, each with its own error and suggestion: daemon absent (`ServiceUnknown`, no activatable name), shell tree absent from the registry (suggest restarting the shell session, never toggling accessibility), watcher absent (suggest enabling the AppIndicator extension, with `ListExtensions` saying whether it is installed and enabled), watcher present and empty (supported-empty). A daemon whose `GetServerInformation` name is not `gnome-shell` returns `PLATFORM_NOT_SUPPORTED` naming the server, because only GNOME is measured (`L21-4`, `L21-5`, `L21-6`, `L21-32`).
- R2. The adapter advertises `Taskbar`, `SystemTray`, `ActionCenter` and `QuickSettings` as snapshot surfaces on GNOME only where U1 measured an open, snapshot, strict-resolve, headed-action round trip for the kind, and `open_system_surface` for each adopts an already-open surface by its `SHOWING` state and otherwise opens it under policy and leaves it open, because the command returns the presented window and the caller then observes it (a notification mutation restores what it opened, R8). Shell roots are found by identity (the registry app that owns `org.gnome.Shell`, its single `window` child) and never enter `list_windows` (`L21-1`, `L21-2`).
- R3. A shell ref survives the normal action preflight: strict resolution, live reads and `hit_test` accept shell roots through a Linux-local shell gate, evidence is role plus name where one exists plus ancestry names with sibling ordinals as tie-breakers only, and a stale or duplicate position returns `STALE_REF` or `AMBIGUOUS_TARGET`, never an action on a neighbour (`L21-18`, `L21-19`, `L21-20`).

**Notifications**

- R4. `list_notifications` returns the entries of the message-list copy only, indexed 1-based in tree order over the unfiltered list (filters never renumber), with `app_name`, `title`, optional `body` and the action labels; the result is identical with the list open or closed; banner copies never appear and never enter the `wait --notification` fingerprint; a list with no entry and either the footer push button outside every entry or the `No Notifications` landmark is an empty result, and any other unreadable or truncated shape is an error; an entry whose labels have not filled in is read again for a bounded time before it is an error (`L21-10`, `L21-14` to `L21-16`, `L32-31`).
- R5. `dismiss_notification` re-reads the list, checks the expected identity against the entry at the requested index, clicks that entry's close button inside the open list, and returns success only when the entry has disappeared from the list copy and the others remain; identical entries are told apart by position and a position that no longer matches is refused (`L21-7`, `L21-11`, `L21-19`).
- R6. `dismiss_all_notifications` with no app filter clicks the clear-all push button once, found as the last push button outside every entry and never by its English name, and verifies every captured entry is gone; with an app filter it closes the matching entries one by one, re-reading after each click, and never uses clear-all; partial failures are returned in the failure list (`L21-13`).
- R7. `notification_action` expands the entry, clicks the named action button, and reports `delivered_unverified` with the daemon's own `ActionInvoked` as evidence when it was observed, or the entry's disappearance when it was not; it never reports the application's effect as verified (`L21-12`).
- R8. Every mutation adopts an already-open list by reading `SHOWING`, opens a closed one by clicking the date menu, and restores the prior state on success, failure, timeout and policy refusal; a list the call did not open is left open (`L21-10`).
- R9. The adapter never calls `CloseNotification`, never infers an id from tree order, and never emits or fabricates `ActionInvoked` or `NotificationClosed`. Doing nothing about Do Not Disturb is deliberate: the setting suppresses banners, not retention, so it changes no listing logic and core has no portable field to report it (`L21-8`, `L21-17`).

**Tray and pointer**

- R10. `snapshot --surface system-tray` shows the tray items with title, `Status`-derived hidden state and a persistent ref bound to the item's unique bus name and object path; items that exist only in the panel (no D-Bus identity) are shown and marked as such; the two measured registration forms (and a defensive, unmeasured slash form) are parsed (`L21-24`, `L21-29`, `L21-30`, `L21-31`).
- R11. Tray activation is delivered as what it is: `Activate` when the item's introspection lists it, `ContextMenu` for a right click when listed, and otherwise, in headed mode, the pointer click on the panel node (which opens the menu, as the user's primary click does). `SecondaryActivate` and `XAyatanaSecondaryActivate` are the item's middle-click action, not its primary action, so they are never sent for a `Click`: a headless `click` on an item that does not list `Activate` is not delivered, and the capability the adapter reports for that item (no `Click`) makes core's actionability gate answer first with `POLICY_DENIED` ("direct semantic delivery is unavailable and physical fallback is denied", `crates/core/src/actionability/gates.rs` `action_supported`), before any adapter call; a direct adapter call (headed without the cursor policy, or the trait used without core's preflight) is refused by name with `ACTION_NOT_SUPPORTED`, `physical_delivery_started: false`, and the suggestion is to retry with `--headed` or to use the item's menu (`L21-25`, `L21-26`). Core's diagnostic for the headless case stays as it is; the named refusal reaching the envelope would need a platform-neutral core change, owner item O7. Core reaches headless delivery only for nodes whose capabilities include `Click` or `RightClick`, so the tray's capabilities are produced from the validated D-Bus operations (KTD10).
- R12. A tray menu pick is `Event(id,"clicked")` on the item's dbusmenu after the adapter has re-read the layout and confirmed the entry exists, is enabled, is not a separator, and belongs to the revision the ref was taken from; a changed revision with a changed entry is `STALE_REF`; a submenu parent is expanded, not clicked; the layout is re-read after a pick for state (`L21-27`, `L21-28`).
- R13. Shell pointer clicks use the centre of valid on-screen extents, refuse extents that do not intersect any display (autohidden dock, invalid sentinel) and not merely a negative origin, are headed-only with the cursor policy checked, and are delivered on X11 through 3.8's primitive and on Wayland through a shell-only RemoteDesktop pointer route whose absence of access on a live session is an honest `ACTION_NOT_SUPPORTED` (`L21-21`, `L21-22`).

**Sandbox, docs, honesty**

- R14. `docs/phases.md` states what was built and no longer states what the evidence disproved: the four false sentences, the incomplete ones, the shell scope enumerated, the dependencies, KDE and other-daemon paths marked unmeasured, the owner items; the `L21` rows enter `probes/linux/FINDINGS.md` (area `L21`) and every row naming 3.14 is disposed of; every deferral is written into the receiving scope in the same PR.
- R15. The three deferred sandbox rows are closed on a disposable root-capable runner: both snap interfaces disconnected and the empty-registry or denied shape recorded, the Flatpak read with and without `--talk-name=org.a11y.Bus` and the exact override text, each in both directions (`L1-18`, `L12-8`, `L12-9`, `L21-35`).
- R16. Isolation and hygiene: `git diff -- crates/core` is empty, no dependency is added (zbus stays `=5.19.0` blocking; no tokio, no atspi crate), no shipped source names a plan, a phase or a decision id, no probe script, capture or box identity is committed.
- R17. The Linux perf method is applied and reported: min-of-seven with the warm-up discarded, reported as min with median and max, for shell discovery, list read, open and restore, a dismiss, an action, tray discovery, a menu pick and one `wait --notification` poll; release size against 15 MiB.
- R18. A stranger dogfood is run and its judged report committed with every finding disposed of.

**Notification identity and signal loss**

- R19. No notification daemon id leaves or enters the adapter. `NotificationInfo` carries the 1-based list index and text only (core has no id field and none is added); the index is the only handle, it is re-validated against the expected app and title on every mutation, and an entry that moved is `NOTIFICATION_NOT_FOUND`. Probe `L21-7` / `L21-8` found no node-to-id association, so this is the shipped behaviour, not a gap (ids are parsed inside the signal reader only and are never stored, returned or put in errors); `list-notifications` output, `NotificationInfo` serialisation and error details are asserted to contain no daemon id (`L21-7`, `L21-8`).
- R20. Every daemon signal is optional evidence and its loss is recovered by the list copy, which is authoritative. `ActionInvoked` and `NotificationClosed` are read from a match rule installed before the click; if the rule was installed late, the signal is dropped by the bus, the reader thread dies or the settle budget ends first, `notification_action` still reports the outcome from the list copy (entry gone, others kept) and names the weaker evidence, never `verified`, and never fails a delivered click as undelivered. `wait --notification` has no signal at all: it compares list-copy fingerprints every poll, so a banner that appeared and left between two polls is still counted if its list copy remains, and the shell's bound of entries per source (`L21-15`) is the stated limit. Recovery is tested by dropping the signal in a fake and by a live run that installs the rule after the click.

**Menu surfaces**

- R21. A popup menu is detected by the structural rule 3.11 uses for `wait --menu` (one function, not a copy), covering GTK3 menu bars and header-bar popovers, GTK4 popovers and context menus, Qt popups and Chromium menu frames, and excluding the idle-true traps (Qt menu-bar items, GTK3 idle menu-family nodes, `HAS_POPUP` nodes, web-content menus) (`L18-1` to `L18-10`).
- R22. `list_surfaces` lists `menu` for the owning process while a menu is open, in the result of the same `click`, `right-click` or `expand` that opened it once the open is observable, and does not list it when closed; `supported_surfaces` gains `menu`, so `snapshot --surface menu` and `find --surface menu` pass validation. `phases.md` §3.4's statement that a `menu` request fails validation by design is corrected in place.
- R23. `snapshot --surface menu --app X` roots at the open popup (not the window), returns its items with roles, names where the toolkit gives one, states (`enabled`, `checked`, `focused`) and refs; a request with no open menu is `ELEMENT_NOT_FOUND` with the open-it suggestion, never an empty tree; the window snapshot's menu-family nodes of a closed menu carry no `showing` state and are not counted as an open menu.
- R24. A menu ref resolves by strict re-identification to the same item while the menu is open and is `STALE_REF` once it closed or re-opened with different content; it survives a second CLI process; actions on it (`click`, `check`, `expand`) pass the ordinary preflight, and a popup whose X11 window is override-redirect or whose Wayland surface is a popup is measured for hit-test and pointer bounds before the kind is advertised (U1 items 12 to 16).

### Scope Boundaries

- In scope, from the 3.7 stranger dogfood (finding 5): the menu surface. Popup menus on GTK3, GTK4 popovers, Qt `QMenu` and Chromium context menus are measured and detected, `Menu` joins `supported_surfaces`, an open menu appears in `data.surfaces` of the action that opened it, and `snapshot --surface menu` roots it. The scope text is in `docs/phases.md` §3.14 (Menu surface).
- No new command, no new `Action` variant, no new `PlatformAdapter` method, no change to a core type or to the C header. Tray and shell interaction use snapshots and refs, as the Windows tray does (`phases.md` P2 tray precedent); there is no `tray` or `dnd` command.
- No Linux code, name, cfg or dependency in `crates/core`.
- No `CloseNotification`, no blind-id probing, no `BecomeMonitor` of `Notify`, no in-memory history: the CLI is stateless per invocation and a monitor started now cannot reconstruct what is already shown (`L21-8`, `L21-36`). Persistent history is the Phase 5 daemon.
- No KDE `GetNotifications` / `org.kde.notificationmanager` / `inhibited` path, no other-daemon path: there is no KDE session on the box and no ledger row, so these are unmeasured, not disproved. They answer `PLATFORM_NOT_SUPPORTED` naming the daemon. This is a deferral on the "infrastructure does not exist" ground; it is written into `docs/phases.md` with its receiving scope and surfaced as owner item O6 because narrowing scope is the owner's call.
- No legacy XEmbed tray: GNOME owns no `_NET_SYSTEM_TRAY_S0` (`L10-13`); panel-only nodes are shown as such.
- No headless notification mutation: there is no non-pointer mechanism (`L21-7`, `L21-11`), so core's existing rejection of headless mutation is correct for Linux and needs no owner change.
- Considered and not built:
  - **A virtual SNI tree as the whole tray surface.** The tray root is the real panel container; only menu entries are virtual children (KTD9). Evidence that would change the call: U1 finding panel nodes missing for visible items.
  - **A blind `CloseNotification` sweep to recover ids.** Rejected on `L21-8`: a hit closes someone else's notification.
  - **Reading Do Not Disturb.** No consumer exists (`L21-17`, KD1).
  - **`Super+V` / Escape as the list opener.** The date-menu click is measured 3 of 3 each way and needs the same pointer route the entry clicks need; a second route adds a keyboard dependency for no gain (`L21-10`).
- Deferred, written into `docs/phases.md` in U2 and U13 with the evidence: the live X11 desktop (non-private) and scale-2 pointer calibration to 3.15's live e2e if U1 cannot produce a scale-2 mode (`L21-22`); KDE and other daemons to the owner's infrastructure item O6; the notification's default (body) action, application-launching actions and keyboard-only traversal, regardless of what U1 item 9 measures: U1 records the measurement and the receiving scope, and implementing any of them needs a new requirement and unit (`L21-36`).

## Planning Contract

### Assumptions

- **3.4 (observation)** landed: registry (`system/registry.rs`, `registry_app.rs`, `registry_frames.rs`), `window_id` codec (`system/window_id.rs`, `decode(&str) -> (bus, path)`), process facts (`system/process_facts.rs`), `observe_tree` (`tree/observe.rs`; its surface gate is the private `require_surface`, which admits only `Window` and `Sheet` today, and its root is decoded by `root_element`, so a shell id with the shell's bus name and the content window's path observes with no new decoder), `list_surfaces` (`system/surfaces.rs`, not `tree/surfaces.rs`, which holds only the sheet predicate `is_sheet`), displays with scale, the connectable-socket display detector (`system/display_server.rs`), and the accessibility `SharedBus`. `LinuxAdapter::supported_surfaces` returns `[Window, Sheet]` in `system/adapter.rs`; that file implements `SystemOps` and has no `open_system_surface` and no notification method today, so U4, U5 and U7 add them there (the trait defaults answer `PLATFORM_NOT_SUPPORTED` until then). `resolve_shell_surface` is an `ObservationOps` method and goes in `adapter.rs`.
- **3.5 (resolution)** landed `resolve_element_strict`, `resolve_locator_anchor` and the window gate in `tree/resolve_gate.rs` (`stored_window(entry) -> StoredWindow`, `StoredWindow::{frame, check_process, check_owner}`). The gate reads `source.source_window_id` and a non-empty `process_instance`, decodes the id, and verifies the owner of the bus name; a shell ref satisfies it as it stands (the shell is a process with readable facts), so U4's edit is the verification of the window itself, not the decoding: where the ordinary path re-lists the inventory, the shell path calls `shell/window_gate.rs`. `RefSource` also carries `source_surface` (`crates/core/src/ref_source.rs`), which is how a menu ref (R24) is told apart at resolve time. U4 and U14 read the file at the cut and the PR names each edit; 3.5 adds no seam.
- **3.6 (actionability)** landed: `tree/hit_test.rs` (`hit_test(bus, handle, point, deadline)` and `hit_test_via<W: HitWorld>`; `HitWorld::facts` reads the window's X11 frame facts, which a shell target has none of), live placement in `tree/live_offscreen.rs` (`placement(bus, element, deadline) -> Placement`; the plan's earlier "calls `live_state.rs` instead of the frame rule" is a branch at the top of `placement`), and `focus_window` in `system/focus_window.rs` (`focus_window(bus, win, lease)`, wired by `system/adapter.rs`), not in `tree/`. The shell branches are three small edits in those three files: `hit_test` (decide by `Contains` plus a display intersection before `HitWorld` is built), `placement` (the shell projection of U4) and `focus_window` (`Ok` with no event for a shell root).
- **3.7 (semantic actions)** landed `actions/dispatch.rs` (`execute_action`) and `actions/physical_delivery.rs`. ### Key Technical Decisions

- KTD1. **Detection is a three-state value, computed from independent facts.** (Evidence: `L21-3`, `L21-4`, `L21-5`, `L21-6`, `L21-32`.) `shell/detect.rs` returns `{daemon, shell_tree, watcher}`, each `Present`, `Absent{why}` or `Unreadable{why}`. Daemon: `GetServerInformation` on the session bus; the name field decides (`gnome-shell`), the owner pid is a helper and is never compared to the shell pid. Shell tree: the registry app whose pid equals the bus owner of `org.gnome.Shell` and whose process `comm` is `gnome-shell` (toolkit `clutter`); its single `window` child is the root. Watcher: `NameHasOwner` on `org.kde.StatusNotifierWatcher`, then `RegisteredStatusNotifierItems` and `IsStatusNotifierHostRegistered`; when absent, `ListExtensions` on `org.gnome.Shell` supplies installed/enabled for the suggestion. A name that vanishes during a read is a retryable transport error after re-reading the name. `toolkit-accessibility` is never consulted. Governs R1.
- KTD2. **Core is untouched; the surface-token mapping uses tokens core already routes.** (Evidence: `crates/core/src/snapshot.rs` routes app-less `Taskbar`, `SystemTray`, `SystemTrayOverflow`, `StartMenu`, `ActionCenter`, `QuickSettings` and not `Dock` / `NotificationCenter`; `L21-23`, `L21-1`.) GNOME's dock maps to `Taskbar`, its message list to `ActionCenter`, its top-panel tray to `SystemTray`, its system menu to `QuickSettings`, matching the Windows meaning of each token. Whether to add `Dock` / `NotificationCenter` routing or ratify this mapping is owner item O1. `StartMenu` (the overview) is not advertised: U1 measures it and the default is not-advertised with the reason written down. Governs R2.
- KTD3. **The shell is its own root; ordinary listings are untouched.** (Evidence: `window_filter.rs` excludes `gnome-shell` and `mutter-x11-frames`; strict window verification re-lists the ordinary inventory; `L21-1`, `L21-2`.) `shell/identity.rs` finds the shell app and its content `window`; `resolve_shell_surface(kind)` returns a `WindowInfo` whose id uses the existing stateless codec with the shell's bus name and the content window's path, and `shell/window_gate.rs` is the verifier that 3.5's gate and `hit_test` consult when the decoded bus name is the shell's; `observe_tree` accepts the shell kinds through a surface branch in `tree/observe.rs`. `list_windows`, `list_apps` and the `mutter-x11-frames` exclusion are not edited. The shell's `window` is a content root, not a helper (`L21-2`). Governs R2, R3.
- KTD4. **Walk to the container, not the shell.** (Evidence: `L21-33`: full walk 1.9 s, list subtree 29 ms, index-chain re-resolve 2.9 ms, 2,056 nodes and depth 21 with 19 entries.) `shell/container.rs` finds the message-list container (the node holding the `Clear all notifications` button or the `No Notifications` landmark), the tray container, the dock panel and the system-menu popup by structure-guided descent from the content root, falling back to the bounded full walk only when the guided descent finds nothing, and keeps the found path in the adapter instance with a landmark re-check before every use (a stale cache re-finds; it is never trusted). A one-shot CLI pays one discovery per process; `wait --notification` and FFI hosts reuse it. The exact descent rules (which siblings to skip: the overview subtree) are fixed by U1. Governs R2, R4, R17.
- KTD5. **The notification reader reads the list copy by structure.** (Evidence: `L21-10`, `L21-14` to `L21-16`.) `notifications/extract.rs` takes `notification` nodes under the message-list container only (banner copies live under a different container at depth 5 and are excluded by ancestry, not by depth), reads labels in order (app, [time], title, [body]) with the time label separated structurally from the header panel U1 identifies (open and closed must produce the same fields; if no structural separator exists the reader uses position plus the measured time-label shape, and U1 says which), action labels from the entry's named `push button` nodes, no markup stripping beyond what the shell already did (an anchor stays raw text, `L21-15`), depth to at least 21 by walking the container subtree with the raw-depth cap 3.4 provides. `notifications/landmark.rs` classifies the container: entries, empty (`No Notifications` with the list readable), unreadable. Indices are assigned over the unfiltered list in tree order before app / text filters and limits, as `crates/windows/src/notifications/list.rs` does. The result is what the shell retains, which is bounded per source (`L21-15`); the skill says so. Governs R4.
- KTD6. **Mutations are one session object around the open list.** (Evidence: `L21-10`; Windows `ActionCenterSession`, macOS `NcSession` as patterns.) `notifications/session.rs` reads `SHOWING` on a list node; if showing, adopts without touching; if not, requires headed policy (focus steal and cursor move), clicks the date-menu node's centre, polls `SHOWING` at the measured cadence (a 40 ms poll flips within the first poll, `L21-33`) under the deadline, and on every exit path (success, error, timeout, drop) closes the list only if this call opened it, verified by `SHOWING` false; a close that does not verify is reported in the error details, never swallowed. Policy is checked before the first event. Governs R5 to R8.
- KTD7. **Per-entry dismiss and action address controls by structure, verified by the list copy.** (Evidence: `L21-11`, `L21-12`, `L21-13`, `L21-19`.) `notifications/dismiss.rs`: re-read the container inside the open session, take the entry at the requested index, compare expected app / title (core's `NotificationIdentity`) against the entry actually read, find the header panel's second unnamed `push button` with valid on-screen extents, click its centre, then poll the captured set: success is the entry gone and every other captured entry still present (multiplicity of `(app, title, body)` decreased by exactly one), not the control's own response. A position whose entry no longer matches is `NOTIFICATION_NOT_FOUND` (the Windows rule, `actions.rs:333`); identical entries leave no way to confirm which one was clicked beyond position and the multiplicity check, which is stated in the result. `notifications/dismiss_all.rs`: no filter is one click on `Clear all notifications` with the captured set verified gone and the banner copy ignored; with a filter it loops per-entry close re-reading after each click (the list reflows), never clear-all, collecting failures. `notifications/action.rs`: expand (first unnamed header button), re-read for the named action button with valid extents, subscribe to `ActionInvoked` and `NotificationClosed` on the session bus before the click (`SessionBus` of 3.8, a match rule, no tokio), click, and report `delivered_unverified` with `action_invoked: <id>` when the daemon signal arrived inside the settle window, else the entry's disappearance as weaker evidence; both are named in the result. The action key / label mapping is the daemon's; the adapter clicks by label. Governs R5 to R7.
- KTD8. **The pointer on a shell target aims at a validated centre.** (Evidence: `L21-21`, `L21-20`, `L21-23`.) `input/shell_aim.rs`: the point is the centre of the node's screen extents, accepted only when the rectangle intersects a display from 3.4's list and is not the sentinel; a rectangle fully outside every display (autohidden dock at `x=-84`, `-2147483648`) is refused with a not-delivered `ACTION_FAILED` naming the extents; a merely negative origin is accepted when it intersects. The effect is read back for the open step (`SHOWING`) and the click step (the entry or node it targeted). `Component.GetAccessibleAtPoint` is not used to confirm a shell target. Delivery: X11 through 3.8's sink (XTEST moves the real cursor, which is why this is headed-only and the cursor policy is checked, `L5-5`); Wayland through 3.8's `RemoteDesktop` with two added pointer methods (no second session type), using relative motion from a clamped origin (four large negative deltas, then relative steps) and button events, the route `L21` used; a missing service or `AccessDenied` is `ACTION_NOT_SUPPORTED` with `physical_delivery_started: false`. Access control on a live session is unmeasured (`L5-3`) and is a Definition of Done line. Governs R13.
- KTD9. **The tray is a real panel container with D-Bus identity attached; only menu entries are virtual.** (Evidence: `L21-29` to `L21-31`, `L21-25` to `L21-28`.) `tray/watcher.rs` reads `RegisteredStatusNotifierItems` and `tray/registration.rs` parses three forms: `name@path`, a bare bus name (path `/StatusNotifierItem`, listed that way for items that register by name), and the unmeasured slash form, which parses but is marked unmeasured and not relied on. `tray/item_props.rs` reads `GetAll` (`Title`, `Id`, `IconName`, `Status`, `Menu`, `ItemIsMenu`; `ToolTip` optional, `L10-10`) and introspects the item for which methods it lists. `tray/panel_correlate.rs` pairs panel `menu` nodes (depth 7, name equal to `Title`) with watcher items only when the title is unique among both lists; duplicate titles are not guessed, they bind by D-Bus identity and the panel node is shown unbound; panel-only items have no D-Bus identity and are marked. The persistent ref binds the **unique bus name** and object path (resolve the registered well-known name to its current owner at observe time and store the unique name); an owner replacement fails closed with `STALE_REF` and a suggestion to re-snapshot, never reaching a restarted service (`L21-30`). Menu entries are children built from `GetLayout(0,-1,[])` (enabled, separator, disabled, checkable with `toggle-state`, submenu parent with `children-display`), identified by menu path plus entry id plus label path plus the layout revision. Whether virtual children satisfy core's identity (`IdentifierKind` has no menu variant; the id lives in `native_id` as `Unknown`) and actionability contracts is demonstrated in U1 before U9 writes code; if it does not, menu picks go through the pointer route on the open popup, whose entries are real labels (`L21-28`), and the D-Bus pick becomes owner item O3. Governs R10, R12.
- KTD10. **Tray activation is chosen by what the item lists and by policy; a secondary method is never substituted.** (Evidence: `L21-25`, `L21-26`; decision: the orchestrator dropped the headless `SecondaryActivate` fallback, formerly owner item O4.) For a `Click` on a bound item: `Activate(x,y)` if introspection lists it (delivery proved by the receiver's log in U11); otherwise, in headed mode, the pointer click on the panel node (the user's primary click, opens the menu) when the policy allows the cursor; otherwise (headless, no `Activate`) the click is refused before any call with `ACTION_NOT_SUPPORTED`, `physical_delivery_started: false`, naming the item and that it lists no `Activate`, with the suggestion to retry with `--headed` or use the item's menu. `SecondaryActivate` is the middle-click action (`L21-26`), not the primary one, and sending it for `click` would deliver an action other than the one requested; the product rule is to refuse what cannot be proved, never to fill the gap with a guess. No code path in this sub-phase calls `SecondaryActivate` or `XAyatanaSecondaryActivate`. **Capabilities come from the same validated operations, for the snapshot and for the live read.** Core's gate reads the capability set (the snapshot's stored `available_actions` and the adapter's `get_live_actions`) and answers `POLICY_DENIED` before dispatch for a `Click` or `RightClick` on a node that lacks the matching capability (`gates.rs` `action_supported`), so the D-Bus methods are unreachable headlessly unless the node reports them. `tray/capability.rs` is the one producer: a tray-bound item reports `Click` only when introspection lists `Activate` and `RightClick` only when it lists `ContextMenu` (never because `SecondaryActivate` exists, and never a capability merely to reach dispatch); a virtual menu entry reports `Click` only when it is enabled, not a separator, and not a submenu parent that has no `AboutToShow` route; a pointer-routed headed click needs no capability because core passes it on policy. The snapshot enrichment (U8) and `get_live_actions` for a tray-bound or menu-entry handle both call it, so the two reads cannot disagree. `RightClick`: `ContextMenu(x,y)` if listed, else the pointer right click in headed mode, else the same refusal. Receivers are unguarded (`L21-27`), so every method call is preceded by a re-check that the unique name still owns the path. Governs R11.
- KTD11. **Menu picks validate on the adapter side, then send.** (Evidence: `L21-27`.) `tray/menu_event.rs` re-reads `GetLayout` for the ref's menu path, confirms the entry id exists at the stored label path, is enabled, is not a separator, is not a submenu parent (a parent gets `AboutToShow` then its children are re-read, not `clicked`), and that the revision matches or the entry is unchanged by identity; then `Event(id,"clicked",data,timestamp)`; then re-reads the layout for state (a checkable's `toggle-state` flips and the revision increments, which is the verification). A mismatch is `STALE_REF`; a disabled entry is `ACTION_FAILED` not delivered, with the reason. The D-Bus menu pick is also the headless route the KTD10 refusal points to, so it works without the cursor. Governs R12.
- KTD12. **Evidence for shell refs is names and ancestry, ordinals last.** (Evidence: `L21-18`, `L21-19`.) The shell gate's identity uses role, name, ancestry names; sibling ordinals break ties only because an extension that inserts a panel child moves ordinals (5 versus 6) while Activities / System menu / date menu keep the same key across open and close. Identical notification entries share every field but ordinal, so a ref that resolves to two candidates is `AMBIGUOUS_TARGET`. Governs R3.
- KTD13. **The bus split is explicit.** Notifications, the watcher, SNI items, dbusmenu and `org.gnome.Shell` are session-bus; the shell tree is the accessibility bus. `SessionBus::get(deadline)` (3.8) is the only session open; no accessibility call goes to it and no D-Bus call here goes to `SharedBus`. A recording fake of each bus in the tests proves the routing. Governs R1, R7, R10.
- KTD14. **Errors keep the three states apart and never fabricate an empty.** A listing that cannot read the container returns an error with the detector's state; a container that reads with the landmark returns empty; a deadline mid-walk is `TIMEOUT`, not a short list. Mutation errors carry `physical_delivery_started` and the session's restore result. Governs R1, R4, R8.
- KTD15. **Sandbox closure runs on a disposable hosted runner.** (Evidence: `L21-35`: the box has snap Firefox with `desktop` and `desktop-legacy` connected, no root to disconnect, no flatpak.) A throwaway workflow job on the branch (deleted before the PR, the vehicle 3.13 uses) with `sudo`: snap leg disconnects `unity7` and `desktop-legacy` (and restores), flatpak leg installs Flatpak and a GTK app, reads with and without the a11y-bus permission, each direction twice. The rows and the exact override text enter the ledger and the docs. Governs R15.
- KTD16. **Layout.** New files by the shared platform layout under the 400-line cap, one concern each, each with `_tests.rs`. `crates/linux/src/system/shell/`: `mod.rs`, `detect.rs`, `identity.rs`, `container.rs`, `kinds.rs` (renamed from `surfaces.rs`, which already exists twice as `system/surfaces.rs` and `tree/surfaces.rs`), `open.rs`, `window_gate.rs`, `hit.rs`, `live_state.rs`. `crates/linux/src/system/menu_surface.rs` and `crates/linux/src/tree/{observe_menu,menu_resolve}.rs` (menu surfaces). `crates/linux/src/notifications/`: `mod.rs`, `landmark.rs`, `extract.rs`, `list.rs`, `session.rs`, `dismiss.rs`, `dismiss_all.rs`, `action.rs`, `signals.rs`, `verify.rs`. `crates/linux/src/tray/`: `watcher.rs`, `registration.rs`, `item_props.rs`, `panel_correlate.rs`, `menu_layout.rs`, `menu_nodes.rs`, `menu_resolve.rs`, `activate.rs`, `menu_event.rs`. `crates/linux/src/input/`: `shell_aim.rs`, `shell_click.rs`. `crates/linux/src/lib.rs` gains `mod notifications;` and `mod tray;`. Edits to existing files are the named, minimal ones in the lane table (`adapter.rs`, `system/adapter.rs`, `system/surfaces.rs`, `tree/observe.rs`, `tree/resolve_gate.rs`, `tree/hit_test.rs`, `tree/live_offscreen.rs`, `system/focus_window.rs`, `actions/dispatch.rs`, `input/wayland/remote_desktop.rs`).

- KTD17. **A menu is an owner-process surface rooted at the popup, not a shell surface and not a window.** (Evidence: `L18-1` to `L18-10`, `L14-13`, `L14-14`, `L3-30`; core: `snapshot_surface.rs` has `Menu` and `Popover`, `snapshot.rs` `is_shell_surface` does not name `Menu`, so core resolves the owner window from the app and hands it to `observe_tree` with surface `Menu`.) `system/menu_surface.rs` calls 3.11's `menu_read` and `menu_open` for the target process and returns the open popups as `MenuPopup { root: AtspiElement, family: MenuFamily }`, `MenuFamily` being `Gtk3Menu`, `Gtk3Popover`, `Gtk4Popover`, `Qt`, `Chromium`, the family only as measured by U1 items 12 to 16 (it selects the root-finding rule, never behaviour of an action). The popup root is the nearest ancestor of the showing item that is a menu (role 33 or 41), or the role-39 container of a GTK3 popover; for Chromium it is the new top-level frame's menu, which `window_filter` excludes from windows (3.11 KTD8), so the root cannot be taken from the window list. Several open popups (a submenu chain) are listed once each, outermost first, and `snapshot --surface menu` observes the outermost whose items are showing. No core change. Governs R21, R23.
- KTD18. **`list_surfaces` and `supported_surfaces` are one decision.** (Evidence: the Windows precedent that an announced surface a snapshot cannot root is a defect, `phases.md` §2.11.) `menu` is advertised if and only if U15's tests show `list_surfaces` lists it and U14's observation roots it for every family U1 measured as snapshottable; a family U1 measured as not observable is named in the `menu` surface's `unclassified` field and in the skill, never silently listed. The extra read in `list_surfaces` is bounded by the same `menu_read` budget, runs only for a process that has a window, and its cost is measured (U1 item 15, the min-of-seven method of R17); if the pruned read costs more than U1 item 15 allows on a 3,000-node Chromium window, the entry is produced from the cheap signals 3.11 documents (opener state `CHECKED`/`EXPANDED`, new top-level frame) and the cost-versus-recall choice is an owner item. Governs R22.
- KTD19. **A menu ref names its popup, not its window.** (Evidence: `RefSource.source_surface`, `L18-6`: the Qt popup is kept in the tree while closed, `L18-7`: the Chromium popup is destroyed.) Evidence is role, name where one exists, the ancestry names up to the popup root, and the sibling ordinal among items (items are often nameless on GTK4, `L3-30`, so ordinal is a primary key here and the weakness is stated: two menus with the same item shape are told apart by the popup root's own identity). `tree/menu_resolve.rs` re-finds the popup by family rule, re-walks to the item, and fails `STALE_REF` with `menu_closed` when no popup is showing, and `AMBIGUOUS_TARGET` on two candidates. The branch is selected by `source_surface == Menu` in 3.5's resolve entry, so ordinary window refs take no new path. Governs R24.
- KTD20. **A menu is found by a state change or a new top-level window, never by toolkit.** (Evidence: `L32-1` to `L32-6`.) The same toolkit has both placements: a GTK 3 menu bar flips `SHOWING` on existing nodes, a GTK 3 context menu is a new nameless role 69 top-level window, a Chromium menu is a new nameless role 23 frame, a GTK 4 popover is a new role 33 subtree inside the window walk, a Qt menu-bar popup is a role 41 child of the opener. `open_popups` therefore reads the application-root children as well as the window walk. A Qt `QLineEdit` context menu does not appear in the tree at all (`L32-5`) and is reported as unobservable, never as an empty menu. Governs R21, R23.
- KTD21. **GTK 4 menu item labels come from the `LABELLED_BY` target.** (Evidence: `L32-7`.) A GTK 4 item has an empty `Name` and `Description`; its `LABELLED_BY` relation (type 2) points at a node whose `Text.GetText(0,-1)` is the visible label. The projection reads that label for menu items only (two extra calls per item) and falls back to the sibling ordinal when the target is missing. GTK 3, Qt and Chromium items carry the label in `Name`; Chromium names include the accelerator text, so a name match on a menu item is a prefix or normalised match. Governs R24.
- KTD22. **The menu entry in `list_surfaces` waits with a bounded settle of about 300 ms on the cheap predicate, only right after an action of the same process.** (Evidence: `L32-8`, `L32-13`.) GTK 4 shows the popover about 260 to 280 ms after the action, GTK 3 context menus and Chromium up to about 350 ms, Qt at once. The settle polls the popup-root `SHOWING` read or the opener-parent child count (under 5 ms per poll), ends at the first success, and is bounded by the remaining deadline; it runs only when the process delivered an action in the last 2 s and the window holds the focus, so a plain `list-surfaces` reads once. Governs R22.
- KTD23. **Closed is "0 nodes" on GTK 4, GTK 3 context menus and Chromium, and `SHOWING` false on GTK 3 menu bars and Qt.** (Evidence: `L32-9`.) The detector reads `SHOWING` and never treats a node's presence as an open menu. An idle GTK 4 window has no menu-family nodes, so the nine nameless items of an earlier dogfood came from an open popup.
- KTD24. **No headed pointer aim is advertised for GTK 4 popups.** (Evidence: `L32-10`, `L32-11`.) GTK 3, Qt and Chromium popups aim with plain screen extents. GTK 4 popup extents have origin 0,0, and the best mapping hit 9 of 15. A GTK 4 menu `click` stays the semantic `click` action until a rule reaches 15 of 15.
- KTD25. **The menu owner is the pid of the active window on X11.** (Evidence: `L32-12`.) In 14 of 14 runs the pid that owns the active window owns the open menu, so an app-less `--surface menu` needs no core route on X11. Wayland is unmeasured and owner item O8 stays open for it.
- KTD26. **A missed `ActionInvoked` has no recovery.** (Evidence: `L32-15`.) The subscription is made before the click. A miss is `delivered_unverified` with the entry-gone read as the evidence, never `verified` and never an undelivered error.

### High-Level Technical Design

*This illustrates the intended approach and is directional guidance for review, not implementation specification.*

```
detect (session bus + a11y registry)           three independent states
  daemon: GetServerInformation -> "gnome-shell"
  tree:   registry app owning org.gnome.Shell -> single `window` child = shell root
  tray:   NameHasOwner(StatusNotifierWatcher) -> items | empty | absent(+ListExtensions)

shell root -> container finder (guided descent, cached path + landmark recheck)
  message list ---- notification entries (list copy)  -> list_notifications
  tray panel   ---- menu nodes (+SNI binding)          -> snapshot --surface system-tray
  dock panel   ---- push buttons                       -> snapshot --surface taskbar
  system menu  ---- popup                              -> snapshot --surface quick-settings

mutation session (headed only):
  SHOWING? --yes--> adopt            --no--> click date menu --> poll SHOWING
  entry: [expand][close]   dismiss  = click close  -> entry gone, others remain
                           action   = click expand -> click named button -> ActionInvoked (daemon)
  list:  [Clear all notifications]  = one click, no app filter
  exit:  restore only what this call opened

tray action: Activate (if listed) | pointer click (headed) | refused ACTION_NOT_SUPPORTED (headless, no Activate)
tray menu:   GetLayout -> validate (exists, enabled, not separator, revision) -> Event(id,"clicked") -> re-read
```

### Sequencing

U1 first. U2 documentation proceeds alongside. U3 and U4 give every later unit its roots and gate. U5 (reader) and U6 (pointer) are independent after U4; U7 needs both. U8 (tray observation) needs U4; U9 needs U8 and U6. U10 is independent. U11 is the live run, U12 the dogfood, U13 the close-out. If the PR exceeds the ~2k guideline the owner may split at the seam notifications (U5, U6, U7) versus tray and sandbox (U8, U9, U10); U3, U4 and U6 go first in either case.

## Probes That Would Change the Design

Each probe names the decision it can flip, so the measurement is read against it.

1. **Menu popup placement per toolkit (U1 item 12, `L32`):** a popup that is a descendant of the window lets U14 walk from the window; a separate application-root child or top-level frame (Qt, Chromium) forces U14 to read the application roots as 3.11's `menu_read` does. A family whose popup cannot be told from its opener in the tree is listed unobservable in KTD18.
2. **Menu item names and states (items 12, 16):** nameless GTK4 popover items (`L3-30`) decide whether ordinal-first refs are acceptable (KTD19) or whether a label source (description, `labelled-by`, child label) must be read for menu items.
3. **Menu timing (item 14):** a menu observable only 157 to 331 ms after the action (`L18-2`) means `list_surfaces` needs a bounded poll inside the action result, which changes the latency of every action; if it costs more than the budget of item 15, the entry comes from the cheap opener-state signals and the choice goes to the owner (O9).
4. **Closed-menu subtree pollution (items 12, 15):** if the nine unnamed `menuitem` nodes of the 3.7 dogfood have `showing` false while closed, the window snapshot can drop them by state, which changes a 3.4 behaviour and is owner item O10.
5. **Popup hit-test and pointer bounds (item 16):** an override-redirect X11 popup or a Wayland popup surface may fail 3.6's `hit_test` or the 3.8 aim; then `menu` is not advertised for that family until a bounds rule exists.
6. **App-less `--surface menu` focus (item 16):** if the focused-window resolution misses a popup that holds the grab, owner item O8 asks core to route `Menu` as `Sheet`, `Popover` and `Alert` are routed.
7. **Notification id association (P2, `L21-7`, `L21-8`; closed):** no association exists, so R19 is shipped behaviour; a daemon or shell that exposes an id would reopen it, which is why the absence is a test.
8. **Missed-signal recovery (item 8):** if a second client's rule does not receive `ActionInvoked` for the sender's notification, the weaker evidence is the only evidence and the `delivered_unverified` wording is checked against what a user can rely on; a reliable signal shrinks the settle budget.
9. **Virtual tray nodes against core identity (item 7):** if a tray handle fails core's `RefEntry` match or the actionability preflight, menu picks use the pointer route (O3); it also decides whether the seven first-line `tray::target_of` edits are needed or only `execute_action`.
10. **Shell refs through the whole contract (item 1) and the X11 pointer (item 2):** a shell ref that fails strict resolve or the live read changes which of 3.5's and 3.6's functions U4 edits and can leave `quick-settings` unadvertised; an X11 pointer that misses the extents' centres changes `shell_aim`.
11. **Container descent cost (item 6):** 29 ms for the list subtree against 1.9 s for the full walk decides whether the cached path is required or a staleness risk.
12. **Tray corner cases (item 11):** `ItemIsMenu`, a missing `Menu` and a revision change between read and pick decide the `AboutToShow` handling and what `STALE_REF` means for a pick.
